## What is frozen

[The input lock](evidence/P004-baseline-lock.json) binds four original inputs to
SHA-256, size, owner/purpose, fixed GitHub endpoints and workflow attempt identity:
verification ZIP, debug-APK ZIP, job metadata and original job log. The original
Android run is **37024421010**, job **110895707817**, attempt **1**.
[The summary](evidence/P004-baseline-summary.json) holds the independently derived
report digest and its principal observations. Neither is generated by reading a
green badge alone. The full report is an output artifact rather than another
large generated document committed into the application.

`baseline.py` reconstructs the Git tree from all **299** source files, validating
membership, mode and blob identity. Source SHA-256 identities remain separate
from generated APK/video/report hashes. It reads every individual host/JUnit
case, including diagnostic lines printed between a test name and its verdict.
Nested JUnit aggregates must agree with their children. Failures and skipped cases
are retained, not filtered. The separately executed permission-denial test is
counted separately from the connected-test XML.

The original accepted software run contains 249 host cases, 340 JVM cases, 62
connected instrumentation cases and one additional isolated permission case.
Its original debug APK is 3,130,891 bytes, SHA-256
`d7809b0c587a4fcfcc74148f0aa76352e551a1e0ad26253c5bad196a91d948ba`.
These are historical executions, not counts of the new P004 tests.

The collector reruns the frozen revision's existing Python consumers on original
exported bytes. This includes FFmpeg full-file decoding of 25 ordinary recordings
(six with audio) and all three P003 adapter families: 5 saved-RAW, 28 ordinary and
5 live attempts. Actual unavailable backends and deliberately failed attempts
remain present. Replay executes only fixed known consumer entry points after
verifying their complete source tree; reports cannot select commands.

The saved-RAW codec route and live backend remain **unavailable** in this emulator.
No live-camera measurement, original-RAW comparison for a normal live take,
physical S23 qualification, dynamic-range gain or native high-resolution claim
is inferred. P003's tested build/emulator/exported-report gate is accepted in this
scope; it is not acceptance of every physical or repeated research condition.

## One-command offline verification

Place the four original files in an input directory, preserving their bytes.
From a full-history checkout with Python 3.10+ and FFmpeg/ffprobe available:

```sh
python3 scripts/baseline.py collect --inputs /path/to/original \
  --reference docs/evidence/P004-baseline-summary.json \
  --expected-head "$(git rev-parse HEAD)" > baseline-report.json
```

This verifies source, execution inventories, media and classified reports against
the frozen reference. It does **not** rebuild Android. To verify a supplied full
report independently, use `verify --report /path/to/report.json` with the same
`--inputs`, `--reference` and `--expected-head` arguments.

For explicit input acquisition (network and GitHub Actions read access required):

```sh
python3 scripts/baseline.py fetch --inputs /path/to/original
```

`GH_TOKEN` is optional when GitHub permits unauthenticated access, otherwise
required by its API. Never put tokens in a lock or command-line argument.
Downloads are create-only, checksum checked, bounded and HTTPS-only; authorization
is stripped on cross-host storage redirects. Existing different bytes are never
overwritten. `collect` and `verify` are offline and read-only, including the Git
index. A missing/expired artifact, unavailable FFmpeg or incomplete record gives a
concrete error rather than an invented pass. Keep an offline copy of the input
bundle: GitHub Actions artifact/log retention is finite. No multi-megabyte
original footage or duplicate APK is added to repository history by P004.

## Clean reproduction is a separate operation

Run **P004 frozen application reproduction** (`baseline-reproduce.yml`). It checks
out the exact original revision on a fresh runner and executes its existing host,
reference, synthetic, Gradle, signing and emulator scripts without editing them.
The workflow revision and application revision are recorded independently. The
baseline SHA is exported inside the command shells; the triggering workflow SHA
must never be mislabelled as the application's source identity.

Original inputs and newly generated artifacts have separate names. The new run
also records `pip freeze`, Java/Gradle/FFmpeg identities, installed SDK package
revisions and the Gradle dependency report. Failures are uploaded even when later
steps cannot run. Generated outputs and debug signing keys may differ: this is
software-result reproduction, **not a claim of byte-identical APKs**.

The existing application pins Gradle/AGP/build-tools/API and checksums, but the
original run did not capture a complete transitive dependency lock. Java major
selection, NumPy version range, runner image and SDK components can resolve
differently. Those limits are reported, not concealed by upgrading the app or
claiming a fully hermetic toolchain. Future exact dependency locking is separate
work supported by the newly recorded inventories.

Create a separately named lock for a newly acquired reproduction dataset, collect
its report, then use `compare --report original.json --other reproduced.json`.
Both reports must first pass their own collectors; comparison is not independent
authentication of arbitrary JSON. It compares source/policy identity and individual
test outcomes while showing software failures, APK differences, tool identities
and backend results separately. Different timing/UUIDs are not erased from the
original reports, nor treated as performance equivalence.

## Acceptance and fault controls

33 focused test methods cover the eight case families. The deliberate baseline
fixture contains a passing host/JVM result, a failed emulator case and unavailable
physical hardware. Its record can be valid while its **softwareResult** is failed.
Do not confuse report consistency with success of all contained experiments.

TC-P004-01 rejects stronger physical claims; -02 rejects stale source/job identity;
-03 requires input ownership and byte provenance; -04 preserves omitted failures,
skips and conflicting aggregates; -05 checks units/domains against the derived
record; -06 preserves policy hashes and historical locks; -07 preserves concurrent
files/index and checks HEAD; -08 exercises isolated reading and missing prerequisites.
Negative controls also cover archive traversal, duplicate entries, links, expansion
limits, token-safe redirects, duplicate cases across test files, failed isolated
instrumentation and mismatched published summary/digest.

```sh
S23_P004_EVIDENCE_DIR=/tmp/P004-cases python3 -m unittest discover \
  -s scripts/tests -p test_baseline.py -v
python3 -m unittest discover -s scripts/tests -v
python3 scripts/verify_master_directive.py
```

The original two failing false-pass tests, subsequent fixes, and three deliberately
introduced collector defects are retained in the handoff evidence. Original CI
failures are never combined with a successful run of another revision. The first
P004 workflow attempt stopped at its source guard and at log retrieval; the
corrected attempt preserves those failures instead of rewriting them.

The separate `baseline-verify.yml` workflow runs the P004 cases and verifies the
original record against its frozen digest. It also collects the independent frozen
execution, checks both datasets, compares the same individual software cases and
retains the first failed workflow attempts separately. If reproduction is pending,
missing or different, it fails rather than turning that gap into acceptance.
